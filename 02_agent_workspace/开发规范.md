# API开发任务规范文档
根据给定 Spec 使用 宿主 框架实现 Handler 类代码，要求：
1. 流程编排：在 Process 函数中编排各业务步骤函数实现业务流程。步骤函数间的数据传递通过在Process函数内定义局部变量来实现。
2. 保证代码可运行：所有函数声明后必须实现。
3. 规范遵循：严格按照 宿主 框架及开发规范编写代码。
4. 可编译通过：确保生成代码无任何编译错误，如有错误需自行修改直至编译通过。

## 通用开发规范
适用于Handler类所有步骤函数的基础约束，需全局遵循：

1. 步骤函数实现规范
- 参数唯一性：同一参数仅在函数入参中传递一次（判断标准：数据类型+字段含义均相同）；
- 参数简洁性：跨函数传递≥3个同结构体的基本类型参数时，直接整体按引用传递原结构体而非单个字段；
- 数据来源：可从成员变量`request_`获取的数据，优先从`request_`读取，其次再从函数入参传入；
- 输出传递：函数输出优先通过返回值传递，其次再通过定义类成员变量来传递；
- 数据在各个函数节点之间传递的过程中，如需转换数据类型或格式，遵循谁使用谁转换原则，提供者按原始数据类型提供。
- 多返回值：优先使用C++17结构化绑定（示例：`auto foo(int x) -> std::tuple<int, int> {};`）。

2. 代码完整性规范
- Drools规则覆盖：单个规则表内的规则按优先级逐个实现，代码中用注释标注对应规则名称/编号；
- 规则信息不完整时，已明确逻辑用真实代码实现，不确定部分标注// TODO: 原因（如“字段来源不明”）。

3. 代码隔离性与职责划分规范
- 步骤函数单一职责：每个步骤函数仅实现对应步骤的业务逻辑，不包含其他步骤的逻辑；
- 函数解耦：步骤函数之间禁止互相调用，仅通过Process函数实现编排串联；
- 职责边界：Process函数仅负责控制流编排（调用步骤函数），不直接实现具体业务逻辑（如字段赋值、API调用等）。

4. 参数校验规范
仅在Drools规则明确要求时进行参数校验，禁止擅自添加任何无规则依据的校验逻辑。

5. API调用规范
- 类型转换：为完成API调用，必要时执行API Request/Response字段的类型转换；
- 响应校验：仅校验Drools规则明确要求的Response参数，禁止以错误消息字段作为异常判断依据；
- 变量命名：无需区分多API的Request/Response时，可简洁命名（如req、resp）；
- 字段补齐：构造Request/Response时，在不违背赋值规则的前提下，补齐所有必填字段（含上下文可确定的、未在赋值规则中出现的字段）；
- 赋值优先级：赋值规则（最高）> 上下文，规则显式赋值的字段以规则为准。
- 来源不明时：无法明确参数数据来源时，需用注释标记 `// TODO` 并说明原因。

6. 异常处理规范
- 框架遵循：严格按Drools规则及宿主框架“异常处理API文档”实现，使用Xwi标准异常机制反馈错误，禁止使用裸露的try-catch；
- 抛出原则：仅当Drools规则明确要求时才抛出异常，摒弃过度防御编程思维；
- 错误匹配：错误码必须与Drools规则的Action一一对应；
- 异常内容：抛出的异常必须同时包含规则指定的错误码和错误信息。
- 当规则中明确指定返回的错误码(返回码)时，一定是当前需求实现的API中定义的错误码，而不是来自该步骤调用的API的错误码。
- 步骤的文档中如果明确表达需要对该步骤调用的API返回的错误码做处理时，才会引用该步骤文档中对应的错误码枚举，在引用时需要在代码中添加相应的头文件，否则会引起编译错误
- 当规则需要判断API调用结果（成功/失败），必须使用 `TryTakeException()` 检查捕获所有异常，不能假设"由框架统一处理"。

7. 头文件引用规范
- 遇到错误码相关的编译错误时，**优先考虑从业务流程步骤的详细信息文档中查找头文件引用**；
- 禁止在编程过程中擅自假设或猜测不存在的头文件，这会导致致命编译错误；
- 可以按需引用必要的C++标准库头文件（如`<cstdint>、<string>`）；

## 专项开发规范
在通用规范基础上，针对特定函数的补充约束：
1. Process函数专项规范
- 流程合规：严格按需求定义的业务流程迭代实现，无功能裁剪/扩展，控制流规则无遗漏；
- 禁止性约束：禁止添加字段校验、异常处理（try/catch/finally）、日志输出语句；禁止在Process函数内进行异常判断、API调用；
- 数据依赖：严格满足数据依赖关系和结构体定义，未明确数据来源标记TODO；不清楚结构体定义时，需参考对应步骤文档，不得假设。

## 编码规范
- 使用C++17来开发(如：整型数据需使用`<cstdint>`中定义的类型如int32_t、uint64_t等)。
- 在保证业务逻辑正确的前提下，编写的C++代码应追求极致的性能(如：避免不必要的对象拷贝，优先使用引用传递)。

### 命名规范
- 避免使用短变量名或符号名。绝不要使用 1-2 个字符的名称。
- 变量 (包括函数参数) 和数据成员名一律小写，单词之间用下划线连接，如：`foo_bar_baz`。
- 函数名应使用动词或动词短语，变量名应使用名词或名词短语。
- 使用有意义的变量名。
- **函数命名禁止与API重名**：该流程调用的API名称如下，函数命名时禁止与这些API名称冲突：
```
无
```

### 控制流规范
避免超过 2-3 层的深层嵌套。

### 注释规范
- 严格依据业务逻辑为代码添加简洁中文注释：解释"为何如此"而非"如何实现"。
- 禁止使用行内注释。注释应置于代码行上方，函数使用语言特定文档字符串。
- 避免TODO注释。直接实现相关功能。

### 代码风格规范
- 遵循已有的代码风格和格式。
- 优先使用多行格式而非单行复合三元表达式。
- 对长代码行进行换行处理。
- 不重构无关代码的格式。

### 函数签名格式
- Google Style的标准C++函数中文Docstring，包括函数说明、入参说明、返回值说明
- 函数签名: auto $优雅的函数名$($参数列表$) -> $返回类型$ {}
- 保证函数名符合函数命名规范。 严格按照以下格式输出：
```
  //
  // 函数说明：
  // ...
  // 入参说明：
  // ...
  // 返回值说明：
  // ...
  auto $函数名$($参数列表$) -> $返回类型$ {};
```
- **函数入参说明**中请简明扼要地注明数据来源，以便在调用函数时能正确地组织数据，来源应参考**当前函数节点所需的外部数据及提供方**并以protobuf中的真实定义为准。
- **函数返回值说明**中无需注明数据来源，且无需说明数据用途，仅说明数据类型、含义即可。
